# Atomic replacement of `config.json` on Windows, macOS, and Linux

This note evaluates the v0.4 contract: stage the replacement in the target directory; preserve the existing mode where meaningful; flush and close the staged file before publication; keep the old target byte-for-byte intact on every reported failure; do not use a backup; do not lock; let the last completed writer win; and refuse symlink mutation.

## Recommendation

There is no single cross-platform operation whose documented failure semantics satisfy every constraint. POSIX `rename` satisfies atomic namespace replacement and its specified failure behavior for ordinary errors, but the standard separately allows an `EIO` failure exception. Windows has replacement APIs, but the documented failure behavior does not provide the required “old target remains intact on every reported failure” guarantee without retaining a backup. Therefore the smallest boring implementation is:

1. Use one shared staged-write sequence: reject a symlink target with `Lstat`, create a uniquely named temporary file in the target directory, write, `Sync`, close, and remove the temporary file on pre-publication failure.
2. On Linux and macOS, publish with `os.Rename(temp, target)`; optionally fsync the containing directory afterward if crash durability of the namespace is required.
3. On Windows, `os.Rename` already requests replacement through Go's internal Windows helper; a build-tagged direct `MoveFileExW` call can add `MOVEFILE_WRITE_THROUGH`. Neither API is documented with POSIX atomicity or the strict failure invariant, so treat it as the smallest best-effort replacement on supported local filesystems, not as proof of the full contract.
4. If the strict invariant is non-negotiable, change one product constraint: permit a temporary backup/rollback name on Windows, or do not promise the invariant on Windows. `ReplaceFileW` is the closest native primitive for metadata preservation, but its documented error `ERROR_UNABLE_TO_MOVE_REPLACEMENT` says that with no backup the replaced file can disappear while the replacement remains under its temporary name.

The likely product decision is to retain atomic replacement on all three systems and explicitly weaken only the Windows “original intact on every reported failure” guarantee. Never implement Windows as `Remove(target); Rename(temp, target)`: that creates a visible missing-target interval and is not atomic.

## What Go `os.Rename` guarantees

Go documents that `os.Rename` replaces an existing non-directory destination. The same documentation warns that, even within one directory, behavior on non-Unix platforms is not atomic. On Unix, the implementation delegates to the platform `rename` system call; on Windows, Go's implementation delegates to its internal Windows rename helper, which uses the Windows replacement-move API. The public API still does not expose a portable replace-and-preserve-failure contract. [Go `os.Rename` documentation](https://pkg.go.dev/os#Rename), [Go Unix implementation](https://raw.githubusercontent.com/golang/go/go1.23.0/src/os/file_unix.go), [Go Windows implementation](https://raw.githubusercontent.com/golang/go/go1.23.0/src/os/file_windows.go), [Go internal Windows syscall source](https://github.com/golang/go/blob/go1.23.0/src/internal/syscall/windows/syscall_windows.go).

On POSIX, `rename(old, new)` replaces an existing non-directory destination in one namespace operation. The destination name remains visible throughout and refers either to the old object or the new object; no observer should see an absent destination or a partially written replacement. If POSIX `rename` fails, the standard says neither the old nor new file is changed or created, except that the specification separately permits an `EIO` failure case. POSIX also says the operation acts on a final-component symbolic link itself rather than following it; consequently, an application that must refuse symlink mutation must check the target with `lstat`/`os.Lstat` before publication, rather than assuming `rename` will reject it. [POSIX `rename`](https://pubs.opengroup.org/onlinepubs/9799919799//functions/rename.html).

Go's Windows implementation does request replacement through its internal Windows rename helper, so `os.Rename` is not the same as a remove-then-rename fallback. That still does not make it a portable POSIX-equivalent: Go's API warns that non-Unix rename is not atomic, and neither Go's documentation nor the Windows API documents the POSIX failure postcondition that the old destination remains unchanged on every error. A direct build-tagged call is useful only when the implementation needs explicit flags such as `MOVEFILE_WRITE_THROUGH`; it cannot manufacture a stronger failure guarantee than Windows provides. [Go Windows implementation](https://raw.githubusercontent.com/golang/go/go1.23.0/src/os/file_windows.go), [Go internal Windows syscall source](https://github.com/golang/go/blob/go1.23.0/src/internal/syscall/windows/syscall_windows.go), [Go `os.Rename` documentation](https://pkg.go.dev/os#Rename), [Microsoft `MoveFileExW`](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw).

`MoveFileExW` documents that `MOVEFILE_REPLACE_EXISTING` replaces an existing destination and that `MOVEFILE_WRITE_THROUGH` waits for a move to be flushed when the move is implemented as copy/delete. It does not state the POSIX-style failure postcondition that the old destination is unchanged on every error. It can also fail because the destination is open without compatible sharing/delete access, so an error is expected under ordinary Windows interference. [Microsoft `MoveFileExW`](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw), [Microsoft moving and replacing files](https://learn.microsoft.com/en-us/windows/win32/fileio/moving-and-replacing-files).

## Stdlib-only feasibility

The common stdlib sequence is feasible for atomic visibility on POSIX: create the temp file in the target directory, write it, call `File.Sync`, close it, then `os.Rename`. It is not sufficient as a cross-platform contract because `os.Rename` does not provide Windows replacement semantics or a documented all-failures-preserve-old guarantee. Go's standard library exposes `File.Sync` for committing file contents to stable storage, but `Sync` is about data durability, not namespace replacement atomicity. [Go `File.Sync` documentation](https://pkg.go.dev/os#File.Sync), [Go `os.Rename` documentation](https://pkg.go.dev/os#Rename).

The staged file must be closed before replacement. This is explicit in Microsoft's file-replacement guidance, and it also avoids publishing a file while the writer still has buffered data. `Sync` should precede `Close`; `Close` alone is not the durability operation. On POSIX, a crash-durable publish additionally needs the containing directory synchronized after `rename`; that is a durability policy, not a requirement for readers to observe an atomic namespace switch. [Microsoft moving and replacing files](https://learn.microsoft.com/en-us/windows/win32/fileio/moving-and-replacing-files), [Go `File.Sync`](https://pkg.go.dev/os#File.Sync), [POSIX `fsync`](https://pubs.opengroup.org/onlinepubs/9799919799/functions/fsync.html).

The unsafe stdlib fallback is `os.Remove(target)` followed by `os.Rename(temp, target)`. It can report success for the remove and then fail the rename, leaving no configuration at all; concurrent readers can observe a missing path. No error cleanup can restore the atomicity that was lost by removing the destination first.

## Native Windows choices

### `MoveFileExW`

The smallest direct Windows adapter is a build-tagged call to `MoveFileExW(temp, target, MOVEFILE_REPLACE_EXISTING|MOVEFILE_WRITE_THROUGH)`; Go's `os.Rename` already uses the replacement flag internally, while the direct call makes the write-through choice explicit. The API explicitly supports replacing an existing file and reports success/failure from the call. It does not promise POSIX failure semantics, does not promise preservation of the target's ACLs/streams/creation metadata, and may reject a target held open without delete sharing. Same-directory operation avoids the API's copy/delete cross-volume behavior, but the contract should still not infer more than the API documents. [Microsoft `MoveFileExW`](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw), [Microsoft moving and replacing files](https://learn.microsoft.com/en-us/windows/win32/fileio/moving-and-replacing-files), [Go Windows implementation](https://raw.githubusercontent.com/golang/go/go1.23.0/src/os/file_windows.go).

`golang.org/x/sys/windows` exposes `MoveFileEx` and its replacement/write-through constants, so this adapter need not use `unsafe` or a hand-written DLL call if adding that first-party Go dependency is acceptable. [x/sys Windows source](https://raw.githubusercontent.com/golang/sys/master/windows/syscall_windows.go).

### `ReplaceFileW`

`ReplaceFileW(target, temp, NULL, 0, NULL, NULL)` is more metadata-aware than `MoveFileExW`: Windows says the replacement inherits/preserves attributes including creation time, short name, object identifier, DACLs, security resource attributes, encryption, compression, and named streams not already present in the replacement. Passing a null backup name meets the no-backup shape at the API-call level. [Microsoft `ReplaceFileW`](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew).

However, it fails the strict failure invariant as documented. For `ERROR_UNABLE_TO_MOVE_REPLACEMENT`, Microsoft says that when no backup was specified the replaced file no longer exists and the replacement file remains under its original name. Other documented errors generally leave both original names in place, but the existence of this explicit exception is enough to reject `ReplaceFileW(..., NULL, ...)` as a proof of “old target intact on any reported failure.” `REPLACEFILE_WRITE_THROUGH` is documented as unsupported, so this API does not replace the separate `Sync` step. [Microsoft `ReplaceFileW`, error table and remarks](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew).

### Handle-based rename information

Windows also exposes handle-based rename information with a replace-if-exists flag; newer `FILE_RENAME_INFORMATION_EX` flags include POSIX-style replacement semantics. This is a lower-level platform-specific implementation, not a portable Go stdlib operation. The Microsoft protocol specification says the POSIX flag makes replacement use POSIX-style semantics for existing handles, but it does not supply the complete cross-filesystem, all-error rollback guarantee required here, and the API requires careful handle access, buffer layout, and OS/filesystem compatibility. It is therefore not the smallest boring v0.4 choice. [Microsoft `FILE_RENAME_INFO`](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info), [Microsoft `FILE_RENAME_INFORMATION_EX`](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fscc/4217551b-d2c0-42cb-9dc1-69a716cf6d0c), [Microsoft `SetFileInformationByHandle`](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setfileinformationbyhandle).

## Mode, ACL, and symlink behavior

On Unix, rename moves the staged file's inode into the destination name; the destination therefore gets the staged file's mode, not the old file's mode. Capture the existing mode with `os.Lstat`, create/chmod the temp to that permission mask before publication, and preserve only the meaningful permission bits requested by the product. Go documents that Unix `Chmod` uses permission bits plus setuid/setgid/sticky bits, while Windows `Chmod` only maps the owner-writable bit to the read-only attribute; the other Go mode bits are unused there. [Go `os.Chmod` source documentation](https://raw.githubusercontent.com/golang/go/go1.23.0/src/os/file.go), [Go `FileMode` documentation](https://raw.githubusercontent.com/golang/go/go1.23.0/src/io/fs/fs.go).

A mode copy is not an ACL/xattr/extended-stream copy. Windows `ReplaceFileW` specifically preserves many old-file attributes and ACL-related data, whereas `MoveFileExW` documents replacement and access checks but not that metadata merge. On POSIX, the staged inode's ACLs, xattrs, ownership, and other filesystem metadata are not made equal to the old inode merely by copying its Go mode; if those metadata are part of the contract, they require platform-specific capture/restore and introduce more failure points. [Microsoft `ReplaceFileW`](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew), [Go `Chmod`](https://raw.githubusercontent.com/golang/go/go1.23.0/src/os/file.go), [Go `FileMode`](https://raw.githubusercontent.com/golang/go/go1.23.0/src/io/fs/fs.go).

Use `os.Lstat`, not `os.Stat`, for the preflight symlink check: Go documents that `Lstat` describes the link itself and does not follow it, including Windows reparse points that are symbolic links or mounted folders. Reject `ModeSymlink` (and, on Windows, the reparse-point classes the product treats as links) before creating/publishing the replacement. The check is necessarily point-in-time when using path-based APIs: another writer can replace the directory entry after the check. A truly race-resistant “never mutate a symlink” guarantee needs descriptor/handle-relative operations and platform-specific no-follow/reparse-point controls; that is beyond portable stdlib and should be stated as an additional constraint if required. [Go `Lstat` documentation](https://raw.githubusercontent.com/golang/go/go1.23.0/src/os/stat.go), [POSIX `rename`](https://pubs.opengroup.org/onlinepubs/9799919799//functions/rename.html), [Microsoft `FILE_RENAME_INFORMATION_EX`](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fscc/4217551b-d2c0-42cb-9dc1-69a716cf6d0c).

## Durability versus atomicity

`File.Sync`/POSIX `fsync` and Windows `FlushFileBuffers` concern flushing file data and metadata to stable storage. Atomic rename/replace concerns the namespace transition observed by concurrent readers. They are independent: a rename can be atomic for readers without being crash-durable, and a flushed temp file can still be published with a non-atomic Windows operation. [Go `File.Sync`](https://pkg.go.dev/os#File.Sync), [POSIX `fsync`](https://pubs.opengroup.org/onlinepubs/9799919799/functions/fsync.html), [Microsoft `FlushFileBuffers`](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers).

For v0.4's stated “flush/close before replace” requirement, call `Sync` and then `Close` on the staged file before the publication call. If crash durability is later added, sync the parent directory after POSIX rename; Windows' `MOVEFILE_WRITE_THROUGH` only adds the documented wait-for-disk behavior for copy/delete moves and does not turn `MoveFileExW` into a documented rollback transaction. [Microsoft `MoveFileExW`](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw), [POSIX `fsync`](https://pubs.opengroup.org/onlinepubs/9799919799/functions/fsync.html).

## Bottom line

* **POSIX/Linux/macOS:** stdlib staged temp + `Sync` + `Close` + `os.Rename` is the smallest implementation that gives atomic namespace replacement and POSIX's documented failure postcondition for ordinary errors (the standard has an `EIO` exception). Copy the old permission bits to the temp first, and reject a pre-existing symlink with `Lstat`.
* **Windows, relaxed failure guarantee:** use the same staging sequence and a build-tagged `MoveFileExW` replacement call for the best available same-volume replacement behavior. Prefer `ReplaceFileW` only if preserving Windows ACL/stream/attribute metadata is more important than its documented no-backup failure hole; it cannot satisfy the strict failure invariant with a null backup.
* **Windows, strict failure guarantee:** no evaluated no-backup API proves it. Permit a temporary backup/rollback strategy or weaken the guarantee. Do not use remove-then-rename.

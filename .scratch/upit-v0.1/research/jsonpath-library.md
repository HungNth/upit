# Go JSONPath library comparison for Upit v0.1

Research date: 2026-09-28. Sources below are RFC 9535, official Go documentation/source, and the candidate projects' tagged source, release metadata, tests, and license files. This note distinguishes a library's capability from the narrower contract proposed for Upit.

## What “standard JSONPath” means here

[RFC 9535](https://www.rfc-editor.org/rfc/rfc9535) is the IETF Standards Track JSONPath specification. It models a query result as a **nodelist**, so a query can produce zero, one, or many selected nodes; it does not define a Go scalar return type. Its selectors include object name, wildcard, array index, array slice, and filter selectors ([§2.3](https://www.rfc-editor.org/rfc/rfc9535#section-2.3)); child and descendant segments are defined in [§2.5](https://www.rfc-editor.org/rfc/rfc9535#section-2.5). Therefore “JSONPath” alone is not enough to define Upit's response-extraction behavior: Upit must choose cardinality, missing-value, and type rules around the library result.

For standard-library decoding, `encoding/json.Unmarshal` documents that JSON objects become `map[string]any`, arrays become `[]any`, numbers become `float64`, and JSON strings, booleans, and null become `string`, `bool`, and `nil` respectively when decoding into `any` ([official package documentation](https://pkg.go.dev/encoding/json#Unmarshal)).

No Upit-specific coercion is supplied by the library. |

## Decision

### Recommendation: `github.com/theory/jsonpath v0.12.1`

Pin **`github.com/theory/jsonpath v0.12.1`** for Upit v0.1. This is evidence-based rather than popularity-based:

1. It is the only compared candidate that explicitly claims RFC 9535 implementation in its package API and README ([`path.go`](https://raw.githubusercontent.com/theory/jsonpath/v0.12.1/path.go), [README](https://raw.githubusercontent.com/theory/jsonpath/v0.12.1/README.md)).
2. Its tagged tests execute the upstream JSONPath compliance suite ([`path_test.go`](https://raw.githubusercontent.com/theory/jsonpath/v0.12.1/path_test.go)); the project changelog records compliance-suite integration and RFC 9535-focused documentation ([CHANGELOG](https://raw.githubusercontent.com/theory/jsonpath/v0.12.1/CHANGELOG.md)).
3. Its public API directly accepts the values Upit already gets from `encoding/json`: string-keyed maps and slices, with explicit empty-result behavior for absent names and indexes ([`path.go`](https://raw.githubusercontent.com/theory/jsonpath/v0.12.1/path.go), [`spec/selector.go`](https://raw.githubusercontent.com/theory/jsonpath/v0.12.1/spec/selector.go)).
4. It is MIT-licensed and has no production dependencies in its module; the tagged README says its dependencies are test-only ([LICENSE](https://raw.githubusercontent.com/theory/jsonpath/v0.12.1/LICENSE), [README](https://raw.githubusercontent.com/theory/jsonpath/v0.12.1/README.md), [go.mod](https://raw.githubusercontent.com/theory/jsonpath/v0.12.1/go.mod)).

The tradeoff is a Go 1.23 minimum ([go.mod](https://raw.githubusercontent.com/theory/jsonpath/v0.12.1/go.mod)) and a v0.x module version. `ojg` has a lower Go floor and a mature, broad API, but its own sources describe a draft/extended dialect rather than RFC 9535; that makes it a worse foundation for a contract that calls itself “standard JSONPath.”

## Minimal Upit v0.1 supported contract

The library remains capable of the full RFC 9535 query language, but Upit SHOULD expose and document this narrower extraction contract:

1. **Input and arrays:** Decode the response with `encoding/json` into the standard tree (`map[string]any`, `[]any`, scalar values). Permit RFC 9535 root/child access, non-negative array indexes (`[0]`, `[1]`, …), wildcards, and filters only where a ticket explicitly needs them; reject any non-supported query syntax at parse time. The library may support negative indexes, slices, descendants, and function extensions, but those are library capability—not automatically part of Upit's v0.1 contract. This keeps the initial contract predictable while leaving the RFC implementation available for expansion.
2. **Missing path:** A query yielding zero nodes is **Missing**, not JSON `null`, an empty string, or a library error. Return an explicit extraction error/status for a required value. A selected JSON `null` is one node and remains distinct; it is not a successful scalar string result.
3. **Multiple matches:** A query used for a scalar uploader field MUST yield exactly one node. Zero is Missing; more than one is a MultipleMatches error. Upit MUST NOT silently choose the first match, concatenate values, or serialize the whole result list.
4. **Scalar coercion/type enforcement:** After the exactly-one check, accept only a scalar of the field's declared target type. For v0.1 URL extraction, the target SHOULD be `string`; a JSON string passes unchanged, while `null`, objects, and arrays fail with a type error. Do not implicitly stringify numbers or booleans: if a future field needs such coercion, define it per field and use a documented canonical representation. This boundary is where Upit enforces typing; neither candidate's `[]any`/`NodeList` return type can enforce it for Upit.

This contract makes “standard JSONPath” executable: RFC 9535 determines query syntax and selection semantics, while Upit determines which selectors it exposes, how zero/many results are reported, and which selected scalar types are valid.
